Short version: you don't create the token directly — you create a **Blob store**, connect it to your project, and Vercel adds the variable for you. Then you pull it locally.

## Dashboard route

1. In the Vercel dashboard, create a Blob store (it's scoped to your account/team, not a single project).
2. Pick **private or public**, a **name**, and a **region**.
3. Open the store's **Projects** tab → **Connect to Project** → choose `replay-ai` and the environments.
4. In your project folder:

```bash
npx vercel link      # once, to connect the folder to the project
npx vercel env pull  # writes the vars into .env.local
```

## CLI route

```bash
npx vercel link
npx vercel blob create-store replay-ai-recordings --access private --region iad1 --yes
npx vercel env pull
```

`--yes` auto-connects it to the linked project. `--region` defaults to `iad1`.

## Two things that are permanent

**Access mode and region cannot be changed after the store is created.** For meeting recordings I'd choose `--access private` — they're user audio, and private means every read needs auth and is served through your own function. Pick the region closest to you and your users; pricing is regionalized.

## You may not get the token at all

This is the part worth knowing: Vercel Blob now authenticates connected projects through **OIDC by default**. When you connect a store, you get `BLOB_STORE_ID`, `VERCEL_OIDC_TOKEN` and `BLOB_WEBHOOK_PUBLIC_KEY`, and the SDK uses those automatically. `BLOB_READ_WRITE_TOKEN` is the long-lived static fallback, and the docs say to use it only when:

- your code runs outside Vercel (CI, another host), or
- you generate client tokens for **browser uploads** via `handleUpload`.

**The second one almost certainly applies to us.** A 45-minute recording is in the hundreds of MB — the design file's own example is a 412 MB MP4 — which is far past what a server-side upload through a function can take. So we'll want client uploads, and that path needs the read-write token. Keeping it in `.env.example` is right.

If the variable isn't in your `.env.local` after `vercel env pull`, you can copy it from the store's settings in the dashboard.

Want me to add `BLOB_STORE_ID` to `.env.example` alongside it, so the OIDC path is documented too? I'd rather do that when we build upload, so the file reflects what the code actually reads.

Sources:
- [Vercel Blob](https://vercel.com/docs/vercel-blob)
- [vercel blob CLI](https://vercel.com/docs/cli/blob)
- [Using the Blob SDK](https://vercel.com/docs/vercel-blob/using-blob-sdk)

## Three decisions worth checking

**I inlined both SVGs as components rather than referencing the files.** Two reasons. An `<img>`-loaded SVG is its own document and can't reach the `next/font` faces, so the illustration's `font-family="Geist"` and `"Newsreader"` fell through to Georgia and system-ui — inlining lets them resolve to the real variables, so the type in the picture matches the type around it. It also drops the ~6KB C2PA metadata block each file carried. The originals stay in `src/assets/` as the source.

**The mark gets a second tone on the teal sidebar.** The asset is a teal tile, which would vanish against the teal panel, so there the tile becomes a translucent white scrim and the bars go white — matching how the design file treats the mark in the sidebar. The glyph is unchanged.

**I put the illustration on the homepage too, which the design file doesn't do.** Its homepage mock is a short browser frame that ends at the four-step grid; at a real viewport height that left a large empty band above the footer. The illustration fills it and states the product's claim in one picture. There's a comment marking it as an addition — say the word and I'll pull it.
