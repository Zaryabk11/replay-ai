Good catch — the retry button does do something, but it's more wasteful than it looks, and that's almost certainly why long recordings needed repeated manual retries.

**What it actually does:** [actions.ts:92-104](src/app/(app)/meetings/actions.ts#L92-L104) resets the meeting all the way back to `UPLOADED` and fires a brand-new `meetingUploaded` event — a fresh Inngest run, not a resume. In [process-meeting.ts:46-57](src/inngest/functions/process-meeting.ts#L46-L57), the only shortcut is "if status is already `READY`, skip." Anything else (including a meeting that got all the way to `SUMMARIZING` before failing) re-runs transcription from scratch — a new Deepgram job, full wait, everything — even though the transcript was already stored successfully. For a long recording, that's minutes wasted per retry before you even get back to the step that actually failed.

**Why "model is very high in demand" needed several retries:** in [gemini.ts:381-396](src/lib/providers/gemini.ts#L381-L396), only HTTP 429 gets special treatment (local backoff + `RetryAfterError` so Inngest retries it specifically). A 503 "model overloaded" response falls through to a plain `Error`, which just gets Inngest's generic `retries: 3` with its default backoff — a few short attempts, not tuned for "capacity's busy, wait a bit." If those 3 exhaust, the meeting lands in `FAILED` and you're back to manually clicking Retry, which — per the above — pays the transcription cost all over again.

Two independent fixes worth doing:
1. **Resume instead of restart**: have `retryMeeting` set status back to whatever stage actually failed (or just leave segments intact and have `process-meeting.ts` skip transcription when segments already exist for that meeting), so a summarization failure only re-runs summarization.
2. **Treat 503 like 429** in `requestGemini` — same `ProviderRateLimitError`/backoff path, since "overloaded" is a capacity signal just like rate-limiting.
